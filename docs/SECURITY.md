# Security & Privacy

## Implemented

| Control | Implementation |
|---|---|
| Authentication | E-mail + password. Passwords are hashed with **Argon2id** (`argon2-cffi`) and re-hashed automatically when parameters change. Password policy (NIST 800-63B style): at least 12 characters, a blocklist of common passwords, and the password must not contain the e-mail name. No composition rules. |
| Sessions | Server-side sessions. A random 256-bit token is set as an **HttpOnly, SameSite=Strict, Secure** cookie (Path `/api`); only its SHA-256 hash is stored. Sessions have an idle timeout (default 120 min) and an absolute lifetime (default 12 h). Sessions are revoked on logout, on "log out everywhere", on password change (other sessions), on role change, on deactivation, on admin password reset and on every restore. |
| CSRF | A per-session token must be sent in the `X-CSRF-Token` header on every POST/PUT/PATCH/DELETE (compared in constant time), in addition to the SameSite=Strict cookie. |
| Brute-force protection | Accounts lock for 15 min after 5 consecutive failures. The API limits each IP to 60 login attempts per 5 min (in-process), and nginx limits `/api/auth/login` to 30/min per IP with a burst of 20. Both are generous because a whole shift may sign in behind one NAT address. Error messages are generic, and the login takes the same time whether or not the e-mail exists (dummy hash verification). |
| Authorization (RBAC) | Roles viewer < analyst < admin, mapped to named permissions (`app/services/auth.py`). **Every** API route declares a permission, enforced by an automated test that enumerates all routes (`test_every_protected_route_declares_a_permission`). A second test (`test_every_api_route_requires_authentication`) calls every route anonymously and expects 401. The UI hides actions the role cannot perform, but the server is the authority. |
| First-login password change | New accounts and admin password resets get a temporary password. Every endpoint except `/auth/*` answers 403 `password_change_required` until it is changed. |
| Destructive actions | Reloading demo data, deleting all data, restoring a backup and deleting a backup require the **admin role, a typed confirmation word and re-entry of the admin's password**, all checked on the server. Reverting an import requires the admin role and `REVERT`. Demo/data-reset tools are **disabled in production** unless `FP_ENABLE_DEMO_TOOLS=true`. Self-lockout protections stop admins from demoting or deactivating themselves or the last admin. |
| Backup integrity | SHA-256 checksums are verified before a restore. Backup names are validated (no path traversal). Only server-created backups can be restored through the API; external dumps are never uploaded through the web interface. The files archive is extracted with Python's `data` filter after rejecting absolute or `..` paths. An automatic safety backup is taken before every restore, and the restore is atomic (`--single-transaction`). Session data is excluded from backups. |
| Audit log | Records **who** did what: user, e-mail, client IP, request ID, timestamp, details. Logged events include sign-in success and failure, lockout, logout, password changes, user management, settings, imports (upload/validate/commit/revert/failure), reports, backups (create/download/restore/delete) and data tools. |
| Request tracing | `X-Request-ID` on every response and in error bodies. The access log includes the user and the request ID. |
| Server-side validation | Pydantic models validate every request body and query parameter. The import is re-validated on the server at commit. |
| Upload limits | Configurable size limit (`FP_MAX_UPLOAD_MB`, default 10 MB), enforced while streaming, plus nginx `client_max_body_size`. Row limit `FP_MAX_IMPORT_ROWS`. |
| File type validation | Only `.csv` / `.xlsx` are accepted. XLSX files must start with the ZIP signature; CSV files must not contain NUL bytes. |
| Safe file processing | Uploads are stored under random UUID names in a private directory that is never served statically. XLSX files are opened in `read_only` + `data_only` mode, so formulas are not evaluated; `defusedxml` is installed. |
| Transactions and duplicates | The import commit and demo reload each run in one transaction. Duplicate import protection uses a SHA-256 file check plus the natural-key unique constraint. |
| Formula injection | Every CSV/XLSX export prefixes text cells starting with `= + - @ \t \r` with `'`. This is tested. |
| HTTP headers | CSP `default-src 'self'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, and `Cache-Control: no-store` on API responses. The nginx version is hidden. |
| Configuration | All secrets come from the environment. There are no default credentials: the first admin is created from `FP_INITIAL_ADMIN_*` (temporary password) or with the CLI. Passwords are never accepted as CLI arguments. |
| Action Center authorization (v0.3) | Permissions `action.read` / `action.write` / `action.manage`, plus object-level checks on the server: only the owner, the creator or an admin can edit an investigation or change its status. Closing, reopening, assigning other users and changing alert rules are admin-only. Only the investigation owner or an admin can verify an action. Closed investigations are read-only. Every change is written to the investigation timeline **and** to the audit log (`investigation.*`, `action.*`, `action_center.*`). |
| Evidence files (v0.3) | Only PDF, PNG, JPEG, CSV and XLSX are accepted, max. `FP_MAX_EVIDENCE_MB` (default 10 MB), enforced while streaming. The extension and magic bytes must match, and CSV must be text. Files are stored under random names in `/data/evidence`, which is never served statically, with a SHA-256 hash. Downloads require a session and are sent as `attachment` with `nosniff` and CSP `sandbox`; there are no public or pre-signed URLs. Removal is a logged soft delete. Evidence files are included in backups and in demo reset / delete-all. |
| Transport security (v0.3.1) | HTTPS mode for LAN installations (`docker-compose.lan.yml`): TLS 1.2/1.3 only, modern AEAD cipher suites, no session tickets, HSTS (1 year), HTTP → HTTPS redirect to `FP_PUBLIC_URL`. Certificates from the company PKI or `ops/generate-tls-cert.sh` (internal ECDSA P-256 CA, SAN, 825 days). Verified: TLS 1.1 rejected, certificate chain/hostname validation, `Secure` cookie not usable over plain HTTP, CSRF enforced through the proxy (`docs/DEPLOYMENT_VERIFICATION.md`). |
| Client IP integrity (v0.3.1) | The bundled nginx is the edge proxy and **overwrites** `X-Forwarded-For` with the connecting address. Before v0.3.1 it appended to a client-supplied header and uvicorn trusted the left-most value, so a client could forge the IP recorded in the audit log and evade the per-IP login limit. Verified with a forged header. |
| Evidence malware scanning (v0.3.1) | Uploads are written to a quarantine directory first. With `FP_EVIDENCE_SCANNER=clamd` (ClamAV INSTREAM) or `command` (any CLI scanner), each file is scanned before it is released; infected files stay quarantined and are **never** downloadable (not even for administrators); scan errors are retried by the worker. Without a scanner (`none`) uploads stay `not_scanned`: ordinary users cannot download them, administrators only with an explicit risk confirmation (audited) or after a justified *release* (audited, timeline). Existing v0.3.0 evidence is treated as unscanned after the upgrade. |
| Evidence reliability (v0.3.3) | **Invariant: ordinary users can download evidence only if the database holds a persisted clean scan result or an administrator release.** The directory a file is in never grants access, and every download is verified against the SHA-256 recorded at upload. File moves follow the commit (transactional outbox `evidence_file_ops`), so a failed commit or a crash can never release a file; failed moves are retried by reconciliation. Uploads are written atomically (staging file + fsync + rename) and deleted again if the database commit fails. Scanner availability is verified by an explicit health check (incl. EICAR detection); an outage does not consume scan attempts and the warning is cleared only by a successful check. Tested with simulated commit failures, worker crashes, failed moves, scanner outage and recovery (`tests/test_evidence_reliability.py`). |
| Background jobs (v0.3.1) | Alert evaluation and re-scans run in a separate worker process, not in user requests (dashboard requests are read-only). Each attempt is one transaction (rolled back completely on failure), recorded in `job_runs` and logged; PostgreSQL advisory locks prevent concurrent runs. |
| Demo data isolation (v0.3.1) | Production installations never receive the synthetic demo dataset unless `FP_SEED_DEMO_ON_STARTUP=true` is set explicitly (warning in the log). Demo placeholder accounts no longer block the bootstrap administrator. |
| No external data transfer | No external AI APIs, analytics, CDNs or web fonts. |

## Known limitations – review before production use

1. **Single company.** `company_id` is on every table and is taken from the authenticated user, but tenant isolation has not been tested with several companies. Do not host several customers in one instance.
2. **No SSO / MFA.** There is no OIDC/SAML integration and no second factor yet. For internet-facing installations, put an authenticating reverse proxy with MFA in front (e.g. Authelia, OAuth2-Proxy, Entra ID Application Proxy).
3. **No self-service password reset.** There is no e-mail flow; administrators reset passwords (UI or CLI).
4. **In-process rate limiting.** The per-IP login limiter is per backend process. The nginx limit and the per-account lockout are global. Revisit this if you run several backend replicas.
5. **TLS certificates** are not renewed automatically (internal CA, 825 days). Plan the renewal; there is no ACME integration for LAN-only host names.
6. **Audit log integrity.** The log lives in the same database, so database administrators can modify it, and a restore resets it to the backup's state (the restore itself is logged afterwards). Forward container logs to a central log system if tamper evidence is required.
7. **Backup encryption.** Backups are not encrypted by the application. Store the off-site copies on encrypted storage.
8. **Synchronous heavy operations.** Report generation and backup/restore run inside the request (with longer proxy timeouts for backups). Very large databases should be backed up with `ops/backup.sh` outside peak hours.
9. **Malware scanning depends on the configured scanner.** Without a scanner, files are only type/signature-checked and stay in quarantine until an administrator releases them – the release decision is a human judgement. ClamAV's detection rate for targeted malware in PDF/XLSX is limited; it is one layer, not a guarantee. The bundled `clamav` container needs outbound access to `database.clamav.net` for signature updates.
10. **Safety observations are administrative records only.** FactoryPulse is not a certified occupational-safety management system and does not replace legally required safety reporting.
11. **Dependency updates.** Versions are pinned. Run `pip-audit` and `npm audit` regularly.
12. **Evidence storage consistency (v0.3.3).** Moves are atomic only within one filesystem (`/data/evidence` and its quarantine must stay on the same volume, as in the shipped compose file). Crash-safety relies on `fsync` and `rename`, as in any POSIX filesystem; network filesystems with weaker guarantees were not tested. Reconciliation and the readiness check `evidence_storage` stat every evidence file, which is fine for thousands of files but not designed for millions. Orphaned files (`evidence/orphaned/`) are kept, not deleted automatically: review and remove them manually. The health check tests that the scanner *works*, not how *well* it detects malware (signature quality remains the scanner's responsibility).

## GDPR notes (Germany/EU)

- User accounts store name, e-mail, role, last sign-in, and IP addresses in sessions and the audit log. Document a retention period for the audit log. Expired sessions are purged automatically after 7 days.
- Production data is normally not personal data. If operator names or IDs are imported (e.g. in free-text downtime reasons), they become personal data. In that case involve the works council (*Betriebsrat*): § 87 (1) no. 6 BetrVG covers systems that could monitor performance, and the audit log of user actions falls under this as well.
- Self-hosting keeps all data on the customer's infrastructure. No third-party processors are involved.
